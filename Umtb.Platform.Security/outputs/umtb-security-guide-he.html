01 / מה החבילה עושה?

Umtb.Platform.Security היא ספריית אבטחה ל־ASP.NET Core שמחברת API לטוקני גישה של Keycloak. היא בודקת מי המשתמש, האם הוא משויך ליישום, ומה מותר לו לבצע. היא גם עוצרת את עליית היישום אם נתיב לא הוגדר עם מדיניות הגנה תקינה או כנתיב אנונימי מפורש.

Authentication — אימות זהות

האם הטוקן חתום, תקף, הונפק על ידי ה־Realm הנכון ומיועד ל־API הזה?

Authorization — הרשאה

האם למשתמש יש קבוצה מותרת ותפקיד שמספיק לפעולה? אחרי זה היישום בודק הרשאה לרשומה עצמה.

רקע שימושי: API מקבל בקשות HTTP; ‏JWT הוא טוקן חתום שמכיל נתונים (Claims); ‏DI מאפשר לקבל שירות כמו ICurrentUser דרך פרמטר או בנאי; Middleware הם שלבי טיפול בבקשה.

החבילה אינה מסך התחברות, אינה מנפיקה או מרעננת טוקנים ואינה מנהלת משתמשים או מסד נתונים. רכיב ההתחברות משיג Access Token מ־Keycloak ושולח אותו ל־API. כל API מאמת בעצמו את הטוקן המקורי.

הגרסה המוגדרת בקוד: 0.1.0-preview.1. יעדי הבנייה: net8.0, net9.0, net10.0. לפי תיעוד האימות במאגר, הפרסום ל־feed עדיין ממתין להחלטה ואישור שחרור; המדריך אינו מניח שהחבילה זמינה ב־nuget.org.

ביישום צרכן עובדים עם ה־API הציבורי. הרחבות עסקיות נכתבות כ־Policies ו־Handlers של היישום.

04 / המסלול של בקשה

  1. התחברותרכיב ההתחברות משיג Access Token מ־Keycloak.
  2. שליחת בקשהAuthorization: Bearer …
  3. אימותחתימה, issuer, audience, זמנים ו־typ.
  4. הרשאת יישוםקבוצה מותרת + תפקיד מספיק.
  5. כלל עסקיבעלות, שיתוף או Tenant לפי היישום.

בנתיב מוגן, טוקן חסר או פסול יוביל ל־401. זהות תקפה שלא עומדת בדרישות תוביל ל־403. לאחר שכל הבדיקות עברו, קוד הפעולה קובע את התגובה.

האימות משתמש ב־discovery וב־JWKS של ה־Authority. ברירת המחדל היא HTTPS ו־RS256; ה־API אינו צריך client secret. נדרשים sub, iat, exp, ‏issuer ו־audience מתאימים ו־typ=Bearer בתוך ה־payload. ‏ID Token ו־Refresh Token אינם תחליף.

תפקידים נקראים רק מתוך resource_access[ClientId].roles. תפקידי Realm או של client אחר אינם מקנים הרשאה כאן. הקבוצות והתפקידים חייבים להגיע כמערכי מחרוזות; מבנה לא תקין אינו מעניק גישה.

תפקיד שהוקצהReadWriteAdmin
readכןלאלא
writeכןכןלא
adminכןכןכן

הטבלה תקפה כשיש גם טוקן תקין וקבוצה מותרת. שם קבוצה כמו /applications/orders/admins לא יוצר תפקיד admin מעצמו. ההתאמה לקבוצות מלאה ורגישה לאותיות גדולות/קטנות; אין התאמת prefix.

05 / שילוב ביישום — צעד אחר צעד

1. משיגים את החבילה

בפרויקט API צרכן, אחרי שה־feed הארגוני או מקור החבילות המקומי הוגדר ב־NuGet, מתקינים את הגרסה המפורשת:

dotnet add package Umtb.Platform.Security --version 0.1.0-preview.1

אם יש רק קוד מקור, השתמשו בפקודות הבנייה והאריזה בהמשך ואז הוסיפו את artifacts/packages כמקור מקומי. אין צורך להעתיק את קובצי Internal ליישום.

2. מגדירים את Security ב־appsettings.json

הכתובת הבאה היא דוגמה: החליפו אותה ב־issuer המדויק של סביבתכם.

{
  "Security": {
    "Authority": "https://identity.example.com/realms/platform",
    "ClientId": "orders-api",
    "Audience": "orders-api",
    "AllowedGroups": ["/applications/orders/users", "/applications/orders/admins"],
    "RoleNames": { "Read": "read", "Write": "write", "Admin": "admin" },
    "GroupsClaimType": "groups",
    "NationalIdClaimType": "national_id"
  },
  "Logging": { "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" } }
}
אפשרותהמשמעות
Authorityכתובת ה־Realm כפי שמופיעה ב־iss. ללא / מסיים, query, fragment או פרטי התחברות.
ClientIdהמפתח ב־resource_access שממנו נקראים התפקידים.
Audienceהערך שחייב להופיע ב־aud. ‏azp אינו תחליף. יכול להיות אותו שם כמו ClientId, אבל נבדק בנפרד.
AllowedGroupsרשימה לא ריקה של נתיבי קבוצות מלאים; נדרשת לפחות התאמה אחת.
RoleNamesמיפוי Read/Write/Admin לשלושה שמות תפקיד שונים ב־Keycloak. ברירת מחדל: read/write/admin.
GroupsClaimType / NationalIdClaimTypeברירות מחדל groups ו־national_id. מזהה לאומי הוא מחרוזת אופציונלית.
AllowedAlgorithmsברירת מחדל RS256; רק האלגוריתמים האסימטריים שהספרייה מתירה.
ClockSkew30 שניות כברירת מחדל; טווח מותר מאפס עד חמש דקות.
AllowHttpDiscoveryInDevelopmentfalse כברירת מחדל. true מותר רק בסביבת Development.

3. רושמים שירותים, מסדרים Middleware ומגינים על נתיבים

using Umtb.Platform.Security;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddUmtbSecurity(builder.Configuration.GetSection("Security"));
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("ApproveOrder", policy =>
        policy.RequireUmtbPermission(UmtbPermission.Write)
              .RequireClaim("department", "operations"));
});

var app = builder.Build();
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/me", (ICurrentUser user) => Results.Ok(new
{
    user.UserId, user.Name, user.Roles, user.Groups,
    user.ExpiresAtUtc, user.RemainingLifetime
})).RequireAuthorization(UmtbSecurityPolicies.Read);
app.MapPost("/write-example", () => Results.NoContent())
   .RequireAuthorization(UmtbSecurityPolicies.Write);
app.MapPost("/admin-example", () => Results.NoContent())
   .RequireAuthorization(UmtbSecurityPolicies.Admin);
app.MapPost("/orders/approve", () => Results.NoContent())
   .RequireAuthorization("ApproveOrder");
app.MapGet("/health", () => Results.Ok()).AllowAnonymous();

await app.ValidateUmtbSecurityEndpointsAsync();
await app.RunAsync();

הסדר חשוב: רישום השירותים לפני Build; ניתוב לפני אימות והרשאה; מיפוי כל הנתיבים לפני ValidateUmtbSecurityEndpointsAsync; הבדיקה לפני RunAsync. הבדיקה אינה מוסיפה Middleware במקומכם.

4. קוראים ל־API

רכיב ההתחברות שלכם מספק Access Token. לדוגמה ב־PowerShell, כשהוא כבר נמצא במשתנה $accessToken וכתובת ה־API במשתנה $apiBaseUrl:

Invoke-RestMethod -Uri "$apiBaseUrl/me" -Headers @{ Authorization = "Bearer $accessToken" }

ללא טוקן, /me אמור להחזיר 401. ‏/health אנונימי במפורש. משתמש עם קבוצה מתאימה ו־read יוכל לקרוא אך לא לכתוב.

06 / מה צריך להכין ב־Keycloak?

זהו מתווה האינטגרציה שמוגדר ב־תיעוד המקומי; השמות להלן הם שמות הדוגמה.

  1. Realm עם issuer מדויק ב־HTTPS. בתיעוד מוצעת התחלה עם חיי Access Token של 300 שניות; זו הגדרה ב־Keycloak, לא מגבלה של החבילה.
  2. Client משאב בשם orders-api עם תפקידי read, write, admin. הוא מיועד ל־API ולא להתחברות משתמשים.
  3. Client התחברות נפרד orders-web עם Authorization Code ו־PKCE S256, כתובות redirect ו־origins מוגדרות במדויק.
  4. Scope ומיפוי שמכניסים את תפקידי orders-api ל־resource_access.orders-api.roles, כמערך מחרוזות. הגבילו את ה־role scope לתפקידים הרלוונטיים.
  5. Audience mapper שמוסיף orders-api ל־aud, ו־Group Membership mapper בשם groups עם Full group path.
  6. משייכים משתמשים לקבוצה מותרת וגם לתפקיד יישום, ישירות או באמצעות מיפוי קבוצות־תפקידים מאושר. אין שיוך אוטומטי ל־read.
  7. ממפים נתוני זהות נדרשים. national_id הוא מחרוזת; מאפיינים מנוהלים כמו nationalId או department אינם אמורים להיות ניתנים לעריכה עצמית.
  8. בודקים טוקן חדש למשתמש משויך ולמשתמש לא משויך באמצעות כלי הסביבה. אל תכניסו טוקן אמיתי לסימולטור כאן — הוא אינו קורא טוקנים.
תרגול מקומי עם סביבת הדוגמה

נדרשים Docker עם Linux engine, ‏Python 3, ‏SDK וכל Runtime שנבדק. מתוך תיקיית החבילה:

docker compose -f keycloak/compose.yaml up -d
dotnet build samples/Umtb.Platform.Security.Sample -c Release
python scripts/keycloak-smoke.py --framework net10.0
docker compose -f keycloak/compose.yaml down

ה־fixture מאזין רק ב־127.0.0.1:18080, משתמש ב־HTTP מקומי ובנתוני בדיקה ללא מסד נתונים מתמיד. הסקריפט מבצע התחברות Code + PKCE ומפעיל את הדוגמה. חשבונות reader, writer, alice, group-only, role-only ו־unassigned מדגימים תרחישים שונים. זו סביבת בדיקות, לא תצורת ייצור.

07 / Controllers, משתמש נוכחי וכללים עסקיים

Controllers

[ApiController]
[Route("orders")]
[Authorize(Policy = UmtbSecurityPolicies.Read)]
public sealed class OrdersController : ControllerBase
{
    [HttpGet]
    public IActionResult Get() => Ok();

    [HttpPost]
    [Authorize(Policy = UmtbSecurityPolicies.Write)]
    public IActionResult Post() => NoContent();
}

נדרשים namespaces של MVC, ‏Authorization ושל החבילה, רישום AddControllers() ומיפוי MapControllers() לפני הבדיקה. המדיניות על ה־Controller ועל ה־Action מצטברת; POST דורש גם Read וגם Write, ותפקיד write מספק את שניהם.

ICurrentUser — מה מקבלים?

UserId הוא sub, ו־Issuer הוא iss. השתמשו בצמד כשיש צורך להבחין בין Realms. ‏Name נלקח מ־name עם fallback ל־preferred_username. ‏Email ו־NationalIdNumber אופציונליים ואינם מפתח משתמש יציב.

Roles מציג רק תפקידים מוכרים שהוקצו בפועל: אם הוקצה admin בלבד, הרשימה אינה ממציאה read ו־write, למרות שהמדיניות מאפשרת את הפעולות האלה. ‏Groups מכיל רק קבוצות מהטוקן שמתאימות ל־allowlist.

IssuedAtUtc ו־ExpiresAtUtc הם זמנים מאומתים; RemainingLifetime הוא הזמן עד exp, חסום באפס וללא ClockSkew. ‏GetClaimValues("department") מחזיר ערכים נוספים. מחוץ לבקשה מאומתת IsAuthenticated=false, השדות הסקלריים null והרשימות ריקות.

IsAuthenticated=true אומר שהזהות אומתה. הוא אינו מבטיח שהמשתמש משויך ליישום או מורשה לפעולה.

כלל עסקי נוסף

המדיניות ApproveOrder בדוגמה מתחילה ב־RequireUmtbPermission(Write) ואז דורשת department=operations. תפקיד admin מספק Write, אבל אינו מבטל את דרישת המחלקה.

הרשאה לרשומה מסוימת

קודם מגינים על הנתיב עם מדיניות החבילה. בתוך הפעולה טוענים את הרשומה תוך סינון Tenant מתאים וקוראים:

var result = await authorization.AuthorizeAsync(http.User, document, "ReadDocument");
return result.Succeeded ? Results.Ok(new { document.Id }) : Results.Forbid();

זהו קטע מתוך זרימה, לא תוכנית עצמאית: נדרשים IAuthorizationService, רשומה ומדיניות עם Handler. בדוגמה המלאה DemoApplication.cs מאפשרים לבעלים או למשתמש משותף לקרוא מסמך, תוך בדיקת issuer. גם admin עשוי לקבל 403 למסמך פרטי. מדיניות משאב פנימית יכולה להתמקד במשאב משום שה־endpoint כבר אכף את דרישות החבילה; אין להשתמש בה לבדה כמדיניות של endpoint.

08 / מעבדת הרשאות

מה צריך לשנות כדי שהבקשה תותר? הסימולציה מניחה נתיב מוגן שעבר את בדיקת העלייה. היא מדגימה את הכללים ואינה מבצעת אימות JWT אמיתי.

ה־allowlist בתרגיל מכיל רק /applications/orders/users. תוצאה מותרת מציינת מעבר בדיקות ההרשאה, לא התחייבות לקוד HTTP מסוים מהיישום.

09 / תקלות נפוצות וגבולות

היישום לא עולה

בדקו שה־Authority תקין, שיש AllowedGroups ושהמיפוי לתפקידים תקין. בכל נתיב צריך מדיניות מפורשת הכוללת את דרישות החבילה או AllowAnonymous. ‏[Authorize] לבדו, RequireRole לבדו, Policy לא רשום או Policy עסקי בלי RequireUmtbPermission אינם מספיקים. קראו לשגרת הבדיקה אחרי כל מיפויי הנתיבים. אל תשנו את Default/Fallback כדי לעקוף את הבדיקה.

401 — בעיית אימות

בדקו נוכחות Bearer, issuer, audience, חתימה, שעון, sub/iat/exp, ‏typ ב־payload וזמינות discovery/JWKS. תקלה ב־discovery אינה בהכרח מפילה טוקן שאפשר לאמת באמצעות מפתחות שמורים; טוקן שלא ניתן לאמת נדחה.

403 — המשתמש מזוהה אך אינו מורשה

בדקו נתיב קבוצה מדויק ותפקיד תחת ClientId הנכון, רמת הרשאה, Claim נוסף וכללי משאב. קבוצה ללא תפקיד או תפקיד ללא קבוצה אינם מספיקים. שינוי שיוכים דורש טוקן חדש שמשקף אותם.

הסרתי תפקיד והמשתמש עדיין נכנס

האימות מקומי. השיוכים בטוקן קיים יכולים להישאר אפקטיביים עד exp בתוספת ClockSkew. בדוגמת טוקן לחמש דקות וסבילות של 30 שניות, הסרה מיד לאחר ההנפקה יכולה להשאיר כ־5:30 דקות גישה. Logout אינו מודיע אוטומטית למאמת המקומי. ביטול מיידי אינו חלק מהגרסה הזאת.

מה עוד באחריות היישום?

סינון רשומות, גבולות Tenant, בעלות, שיתוף, הסתרת קיום רשומה באמצעות 404 לפי הצורך, והגנה על Middleware שמחזיר תגובה לפני ניתוב והרשאה. ביקורת הנתיבים אינה סורקת תשובות של Static Files או terminal middleware.

הגרסה מיועדת לטוקני משתמש, ל־Realm/Client אחד לכל API ולהגדרות קבועות בזמן העלייה. Service accounts, ריבוי issuers, שינוי מדיניות דינמי וביטול מיידי אינם נתמכים במתווה V1 המתועד.

איך מאבחנים בלי לחשוף מידע?

אירוע 1001 מציין כישלון אימות, 1002 Bearer challenge, ‏1003 דחיית הרשאה, 1101 נתיב אנונימי ו־1102 כישלון ביקורת נתיבים. לוגי החבילה אינם כוללים טוקנים או מזהים אישיים. הגדרות הלוגים של היישום, הפרוקסי והמסגרת הן באחריות המארח; אין לרשום Authorization headers.

10 / פיתוח ובדיקת החבילה עצמה

פקודות אלה מיועדות לתיקיית החבילה, לא לפרויקט API צרכן. לפי README נדרש SDK של .NET 10; להרצת כל מטריצת הבדיקות נדרשים גם ASP.NET Core runtimes של 8, 9 ו־10. הבדיקות אינן מסתפקות ב־roll-forward לגרסה ראשית אחרת.

dotnet restore Umtb.Platform.Security.slnx
dotnet build Umtb.Platform.Security.slnx -c Release --no-restore
dotnet test tests/Umtb.Platform.Security.Tests -c Release --no-build --no-restore
python scripts/verify-docs.py
dotnet pack src/Umtb.Platform.Security/Umtb.Platform.Security.csproj -c Release --no-build -o artifacts/packages
python scripts/verify-package.py artifacts/packages/Umtb.Platform.Security.0.1.0-preview.1.nupkg

בפיתוח, הדוגמה והבדיקות מפנות לפרויקט המקור. בדיקת שחרור משתמשת ב־UsePackedPackage=true וב־cache נקי כדי לבדוק את החבילה שנארזה בפועל. ההוראות המלאות ב־releasing.md.

רשומת verification.md מתאריך 04.10.2026 מתעדת 131 בדיקות לכל יעד, בדיקות צרכן ארוז ואימות Keycloak. אלה תוצאות מתועדות במאגר; הן לא הורצו מחדש במסגרת הכנת המדריך.

12 / מילון ומקורות מתוך הקוד

Realm
תחום זהויות ב־Keycloak; הכתובת שלו היא issuer של הטוקן.
Client
יישום רשום ב־Keycloak. Client התחברות ו־Client משאב ממלאים תפקידים שונים.
Claim
ערך בטוקן, כגון sub, קבוצות או department.
Policy / Requirement / Handler
Policy אוספת דרישות; Requirement מייצגת תנאי; Handler בודק אם הוא מתקיים.
JWKS
מפתחות ציבוריים המשמשים לאימות חתימות של טוקנים.
Scoped
משך חיים של שירות DI בטווח הבקשה, כפי שנרשם ICurrentUser.
